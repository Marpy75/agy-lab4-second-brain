# Second Brain Assistant Skill

Ця навичка перетворює агента на персонального асистента з організації та структурування бази знань «Second Brain». Вона автоматизує аналіз конспектів, їх розподіл за категоріями PARA, створення зв'язків між темами та оновлення метаданих згідно з архітектурними стандартами системи.

---

## 1. Головні правила та обмеження (Invariants)

Агент **зобов'язаний суворо дотримуватися** таких правил:

1. **Ніколи не вигадувати джерела**:
   - Поле `source` у Frontmatter та посилання на першоджерела в тексті повинні заповнюватися **тільки** якщо джерело явно вказано користувачем або чітко міститься в тексті нотатки (наприклад, посилання на репозиторій, конкретний підручник, лекцію, слайд).
   - Якщо достовірне джерело відсутнє — залишити поле порожнім: `source: ""`. Заборонено генерувати вигадані книги, статті або сайти.

2. **Зберігати оригінальний зміст нотатки**:
   - Авторський контент, конспекти, формули, коментарі, фрагменти коду та висновки користувача є недоторканими.
   - Дозволяється додавати структуру, блоки заголовків, резюме та метадані, але **заборонено видаляти, скорочувати чи спотворювати** змістовну авторську частину.

3. **Дотримуватись моделі нотатки з `docs/architecture.md`**:
   - Кожен файл повинен мати коректний YAML Frontmatter на початку.
   - Обов'язкові поля метаданих:
     - `title`: Людинозрозуміла назва нотатки (рядок у подвійних лапках).
     - `created`: Дата створення у форматі `YYYY-MM-DD`.
     - `updated`: Дата поточного оновлення у форматі `YYYY-MM-DD`.
     - `type`: Тип матеріалу — строго один із: `"lecture"`, `"lab"`, `"seminar"`, `"concept"`, `"literature"`.
     - `status`: Життєвий цикл — строго один із: `"inbox"`, `"in_progress"`, `"completed"`, `"archived"`.
     - `tags`: Масив рядків у нижньому регістрі (`lowercase`).
     - `source`: Рядок першоджерела або `""`.
   - Рекомендована структура Markdown:
     - Заголовок першого рівня `# {{title}}`
     - Секція `## Короткий зміст`
     - Секція `## Технічні деталі та код` (за наявності коду чи формул)
     - Секція `## Пов'язані матеріали (Backlinks)`

4. **Імена файлів — виключно латиницею**:
   - Імена файлів повинні містити лише латинські літери нижнього регістру, цифри, дефіси та підкреслення (`kebab-case`).
   - Обов'язкове розширення: `.md` (наприклад, `cache-memory-organization.md`, `pipeline-hazards.md`).
   - Жодної кирилиці, пробілів чи спеціальних символів у назвах файлів. Якщо вихідна нотатка мала кириличну назву, запропонувати коректний транслітерований або англомовний slug.

5. **Не видаляти та не переміщати файли без підтвердження користувача**:
   - Будь-яке переміщення між категоріями PARA (наприклад, з `notes/Inbox/` до `notes/Areas/`) або перейменування файлу **вимагає явного підтвердження користувача**.
   - Спочатку агент формує план дій і пропонує його користувачеві. Фізичні операції переміщення/перейменування виконуються тільки після схвалення.
   - Фізичне видалення файлів з диска заборонене — для видалення використовується м'яке переміщення до `notes/Archives/` зі зміною статусу на `archived`.

6. **Обов'язкове формування журналу запропонованих змін**:
   - Наприкінці кожної сесії обробки нотаток агент зобов'язаний вивести структурований журнал (Changelog) із переліком усіх пропозицій.

## 2. Критерії класифікації PARA

Розподіл за каталогами в папці `notes/` здійснюється за такими принципами:

| Категорія | Призначення у навчальному контексті | Рекомендований `status` | Приклади |
| :--- | :--- | :--- | :--- |
| **`notes/Inbox/`** | Тимчасовий вхідний буфер для сирих конспектів, швидких заміток під час лекцій, чернеток без метаданих. | `inbox` | `lecture-raw.md`, `draft-notes.md` |
| **`notes/Projects/`** | Матеріали з конкретними дедлайнами, завершеними цілями та критеріями готовності (лабораторні, курсові, підготовка до колоквіуму). | `in_progress`, `completed` | `lab1-cache-sim.md`, `course-project-cpu.md` |
| **`notes/Areas/`** | Довгострокові навчальні предмети та сфери відповідальності студента без конкретної кінцевої дати (навчальні дисципліни семестру: АСКС, Архітектура ЕОМ, ОС). | `in_progress` | `pipeline-architecture.md`, `memory-hierarchy.md` |
| **`notes/Resources/`** | Довідкові матеріали, бібліотеки алгоритмів, шпаргалки, конспекти підручників, корисні посилання для багаторазового використання. | `in_progress`, `completed` | `riscv-isa-cheatsheet.md`, `git-workflows.md` |
| **`notes/Archives/`** | Завершені проєкти, матеріали минулих семестрів, застарілі чи м'яко видалені нотатки. | `archived` | `archived-coursework-2025.md` |

## 3. Покроковий алгоритм роботи навички

### Крок 1. Сканування середовища та контексту
1. Перевірити наявність нових або необроблених нотаток у каталозі `notes/Inbox/` або прочитати конкретний файл, вказаний користувачем.
2. Просканувати заголовки та назви файлів в усій директорії `notes/` (`Projects`, `Areas`, `Resources`, `Archives`), щоб мати актуальний реєстр існуючих тем для перехресних посилань.

### Крок 2. Аналіз та структурування нотатки
1. Прочитати вміст нотатки, виділити її основну тему, ключові поняття, дисципліну та наявні кодові фрагменти.
2. Сформулювати чітку людинозрозумілу назву (`title`).
3. Визначити відповідну категорію PARA згідно з розділом 2.
4. Встановити тип матеріалу (`type`):
   - `lecture` — конспект лекції;
   - `lab` — лабораторна робота або практичне завдання;
   - `seminar` — практичне/семінарське заняття;
   - `concept` — окреме поняття, термін чи архітектурний принцип;
   - `literature` — огляд статті, розділу підручника чи документації.

### Крок 3. Нормалізація тегів
1. Підібрати 2–6 лаконічних тегів, що характеризують предметну область та технологію.
2. Перевести всі теги у нижній регістр (`lowercase`), без пробілів (використовувати дефіси при потребі):
   ```yaml
   tags:
     - "аскс"
     - "конвеєр"
     - "mips"
     - "hazards"
   ```
3. Узгодити теги з уже існуючими в базі нотаток, уникаючи синонімічного дублювання (наприклад, не змішувати `pipeline` та `конвеєри`, якщо в базі вже закріплено `конвеєр`).

### Крок 4. Стисле підсумовування (Summarization)
1. Скласти або оновити секцію `## Короткий зміст`.
2. Резюме повинно містити:
   - 2–4 ємні речення з визначенням та головною ідеєю матеріалу;
   - маркований список 3–5 ключових тез.
3. Не змінювати і не скорочувати тіло авторського контенту нижче за резюме.

### Крок 5. Пошук зв'язків та генерація Backlinks
1. Порівняти ключові терміни поточної нотатки з реєстром `title` наявних нотаток у Second Brain.
2. Якщо знайдено тематичний або концептуальний перетин, додати посилання у форматі `[[Назва нотатки]]`.
3. Зв'язки можна інтегрувати природно в текст або зібрати у фінальному блоці:
   ```markdown
   ## Пов'язані матеріали (Backlinks)
   - Див. також: [[Методи усунення структурних конфліктів]]
   - Реалізація в проєкті: [[Лабораторна робота 1]]
   ```

### Крок 6. Запит на підтвердження дій над файлами
1. Сформувати нове ім'я файлу латиницею (якщо оригінальне було некоректним або містило кирилицю).
2. Запитати підтвердження у користувача перед будь-яким переміщенням чи перейменуванням:
   > **Запит на дію з файлом:**
   > - Поточний файл: `notes/Inbox/нова_лекція.md`
   > - Цільовий шлях: `notes/Areas/pipeline-structural-hazards.md`
   > - Чи підтверджуєте ви переміщення та перейменування файлу?

### Крок 7. Запис змін (після підтвердження)
1. Згенерувати оновлений файл із валідним YAML Frontmatter.
2. Оновити мітку `updated` на поточну дату у форматі `YYYY-MM-DD`.
3. Записати файл за схваленим шляхом.

### Крок 8. Формування підсумкового журналу змін
Наприкінці відповіді обов'язково надати звіт за встановленим шаблоном:

```markdown
### Журнал запропонованих змін

| Параметр | Поточне значення | Пропозиція / Нове значення |
| :--- | :--- | :--- |
| **Файл / Шлях** | `notes/Inbox/нова_лекція.md` | `notes/Areas/pipeline-structural-hazards.md` |
| **Title** | `нова_лекція` | `"Структурні конфлікти конвеєра"` |
| **Категорія PARA** | `Inbox` | `Areas` (навчальна дисципліна АСКС) |
| **Type** | — | `lecture` |
| **Status** | `inbox` | `in_progress` |
| **Tags** | `[]` | `["аскс", "процесори", "конвеєр"]` |
| **Source** | — | `"Лекція №3, слайд 14"` (з тексту) / `""` |
| **Зв'язки (Links)** | — | `[[Конвеєризація процесорів]]`, `[[Лабораторна 1]]` |
| **Короткий зміст** | — | Додано блок `## Короткий зміст` із 3 ключовими тезами |
| **Статус дії** | Очікує підтвердження користувача на переміщення |
```

## 4. Еталонний шаблон нотатки

```markdown

title: "Структурні конфлікти конвеєра"
created: "2026-11-01"
updated: "2026-11-01"
type: "lecture"
status: "in_progress"
tags:
  - "аскс"
  - "процесори"
  - "конвеєр"
source: "Курс АСКС 7 семестр, лекція 3"
---

# Структурні конфлікти конвеєра

## Короткий зміст
Структурні конфлікти виникають, коли кілька інструкцій на різних стадіях конвеєра одночасно звертаються до одного апаратного ресурсу (наприклад, спільної пам'яті інструкцій і даних або одного АЛП).
- Конфлікт ресурсів призводить до затримки (stall/bubble).
- Основним рішенням є розділення пам'яті (гарвардська архітектура) або дублювання функціональних блоків.

## Технічні деталі та код
```c
// Вставка бульбашки (bubble) у конвеєр при конфлікті
void insert_bubble(Pipeline *p) {
    p->stage_id.nop = true;
}
```

- Див. також: [[Методи оптимізації конвеєра]]
- Базова концепція: [[Основи конвеєризації]]
```
